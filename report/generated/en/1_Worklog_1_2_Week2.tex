\vspace{0.5em}\noindent\textbf{Technical Implementation}\par

Concurrency control was implemented at the database and API-contract
level:

\begin{itemize}
\tightlist
\item
  PostgreSQL unique constraints protect duplicate user, company,
  application, and idempotency records.
\item
  \texttt{Idempotency-\allowbreak{}Key} is accepted for candidate application
  submission and selected workflow commands.
\item
  Reusing the same idempotency key with the same payload replays the
  stored response.
\item
  Reusing the same idempotency key with a different payload returns
  \texttt{409} with \texttt{idempotency\_\allowbreak{}key\_\allowbreak{}reused}.
\item
  Mutable HR job and application commands require
  \texttt{expectedVersion}.
\item
  Stale version updates return controlled \texttt{409\ Conflict}
  responses.
\item
  Chat retries use deterministic client message IDs and DynamoDB
  conditional write behavior to avoid duplicate logical messages.
\end{itemize}

Conflict flow:

\textbf{Flow summary.} A client submits an application with an
idempotency key. The backend reserves the key in PostgreSQL, creates the
application for a new request, returns the stored response for an exact
replay, and returns HTTP 409 when the payload or business state
conflicts.

\vspace{0.5em}\noindent\textbf{Weekly Results}\par

My Week 2 result was a deployment-focused review of the team's
database-backed concurrency policy and its behavior with multiple
replicas. The backend and chat implementations themselves were owned by
the teammates responsible for those components.

\vspace{0.5em}\noindent\textbf{Lessons Learned}\par

Service load balancing does not serialize writes. Correctness must be
enforced at the storage and transaction boundary, then reflected clearly
through API response codes and UI behavior.

\vspace{0.5em}\noindent\textbf{Next Week Plan}\par

Build the transactional outbox and asynchronous processing layers so
committed domain changes can trigger reliable downstream work without
keeping the main API request open.
